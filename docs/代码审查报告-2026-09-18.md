## P0 — 可能导致崩溃

### 0.1 `AppStateSaver` 把邮件 HTML 全文写进 Bundle，存在 `TransactionTooLargeException` 风险

**位置**：`MainActivity.kt:1812-1844`（`appStateToJson`）；触发点 `:531`（`rememberSaveable(stateSaver = AppStateSaver)`）

**问题**：`rawMessages` 已经在 `:1833` 做了 `takeLast(5)` 限流，但 `items` 在 `:1821-1831` **没有任何条数限制**，且每条都写入 `htmlBody`（完整邮件 HTML）。验证邮件/营销邮件的 HTML 动辄 30-100 KB，10 封邮件即可轻松越过 Binder 事务上限（约 500KB~1MB），在**旋转屏幕或进程重建**时抛 `TransactionTooLargeException` 崩溃。

**建议改法**：

```kotlin
// appStateToJson 内
val items = JSONArray()
state.items.takeLast(20).forEach { item ->          // 加条数上限
    items.put(JSONObject().apply {
        put("from", item.from)
        put("subject", item.subject)
        put("time", item.time)
        put("body", item.body.take(2000))           // 正文截断
        put("ts", item.timestamp)
        // 不再写入 htmlBody
    })
}
```

**权衡**：不保存 `htmlBody` 意味着进程重建后再次打开该邮件只能显示纯文本正文（`body` 已是 `stripHtml` 结果，可读）。若必须保留富文本，改为只存前 1-2 封的 `htmlBody`，或重建后重新拉取。

## P1 — 明确 Bug / 可见错误

### 1.1 深色模式下状态栏图标不可见

**位置**：`MainActivity.kt:527`（`enableEdgeToEdge()`）

**问题**：`enableEdgeToEdge()` 无参调用的默认 `SystemBarStyle.auto()` 按**系统**夜间模式判定 `isAppearanceLightStatusBars`，而本应用的深色开关是 `state.isDarkMode`（来自 SharedPreferences，默认 `false`，`TempMailTheme` 显式传入，见 `:713`），**与系统设置完全独立**。

后果：

| 系统 | App 内开关 | 图标颜色 | App 背景 | 结果 |
|---|---|---|---|---|
| 亮色 | 深色 | 深色图标 | `#121212` | **图标不可见** |
| 深色 | 亮色 | 浅色图标 | `#F8F9FA` | **图标不可见** |

**建议改法**（在 `MainActivity.onCreate` 的 `setContent` 内）：

```kotlin
val view = LocalView.current
LaunchedEffect(state.isDarkMode) {
    val window = (view.context as? android.app.Activity)?.window ?: return@LaunchedEffect
    androidx.core.view.WindowCompat.getInsetsController(window, view).apply {
        isAppearanceLightStatusBars = !state.isDarkMode
        isAppearanceLightNavigationBars = !state.isDarkMode
    }
}
```

需要补 `import androidx.compose.ui.platform.LocalView`。

### 1.2 WebView 从不销毁，每打开一封邮件泄漏一个实例

**位置**：`MainActivity.kt:1097-1173`（`AndroidView { WebView(ctx) }`）；`:1106-1135`（`onCreateWindow` 内新建的弹窗 WebView）

**问题**：全文件 `grep destroy|DisposableEffect|onRelease` **零命中**。`showBodyDialog` 关闭时 `if (showBodyDialog) { ... }` 整块离开组合，View 被 detach 但 WebView 的原生资源未释放；下次打开邮件又新建一个，泄漏随打开次数线性累积。`onCreateWindow` 里为处理 `target="_blank"` 而创建的临时 WebView 同样从不销毁。

**建议改法**：给 `AndroidView` 加 `onRelease`（Compose UI 1.5+ 支持，当前 BOM 2024.01.00 = ui 1.5.4，可用）：

```kotlin
AndroidView(
    factory = { ctx -> WebView(ctx).apply { /* 现有配置不变 */ } },
    onRelease = { webView ->
        webView.stopLoading()
        webView.loadUrl("about:blank")
        webView.destroy()
    },
    modifier = Modifier.fillMaxWidth().heightIn(min = 200.dp, max = 400.dp)
)
```

`onCreateWindow` 内的弹窗 WebView 建议在拦截到链接后销毁（先实现主 WebView 的 `onRelease` 收益最大；弹窗路径改动后需回归验证 `target="_blank"` 链接仍可跳转）。

### 1.3 手动"检查更新"会把 GitHub 限流/错误误报为"已是最新版本"

**位置**：`MainActivity.kt:640-647`

**问题**：GitHub 未认证 API 限流 60 次/小时。触发限流时返回的是 HTTP 403 + `{"message":"API rate limit exceeded...", ...}`，这个响应**能**被 `JSONObject(body)` 正常解析，于是：

```kotlin
val tag = j.optString("tag_name", "").removePrefix("v")   // → ""（字段不存在）
if (versionCompare(tag, cur) <= 0)                        // versionCompare("", "1.9") → -1
    if (isManual) ... snackbar.showSnackbar(s.alreadyLatest)   // 显示"已是最新版本"
```

同理，任何非 Release 的 JSON 响应都会被误判为"已是最新版本"，用户被误导为已检查成功。

**建议改法**：在版本比较前加字段存在性校验：

```kotlin
val tag = j.optString("tag_name", "").removePrefix("v").trim()
if (tag.isBlank()) {
    // 非 Release 响应（限流 / 网络拦截页 / API 变更）
    if (isManual) withContext(Dispatchers.Main) {
        scope.launch { snackbar.showSnackbar(s.updateFail) }
    }
    return@launch
}
```

### 1.4 验证码兜底正则过宽，且 `(?!20\d{2})` 逻辑写错

**位置**：`MainActivity.kt:1769`

```kotlin
Regex("(?:^|\\s|\\n|\\r)((?!20\\d{2})[0-9]{4,8})(?:\\s|$|\\n|\\r|\\.|,)")
```

**两个问题**：

1. **误报**：这条兜底规则会命中邮件里**任意** 4-8 位数字 —— 订单号、快递单号、电话号码片段、金额。用户会看到一个复制了错误值的"复制验证码"按钮。
2. **漏报（逻辑错误）**：`(?!20\d{2})` 的本意是排除 4 位年份，但它只检查**前 4 个字符**。因此任何以 `20XX` 开头的 4-8 位数字都被整体拒绝：

   | 邮件中的数字 | 是否命中 | 期望 |
   |---|---|---|
   | `2024`（年份） | 否 | 否 ✅ |
   | `202501`（6 位验证码） | **否** | 是 ❌ |
   | `201234`（6 位验证码） | **否** | 是 ❌ |

**建议改法**（保留 `\s` 已覆盖 `\n\r` 的事实，并修正 lookahead 语义）：

```kotlin
// 仅当"20XX"整体就是一个 4 位数字（后面不接数字）时才排除
Regex("(?:^|\\s)((?!20\\d{2}(?![0-9]))[0-9]{4,8})(?:\\s|$|\\.|,)")
```

验证：`2024` → 排除 ✅；`202501` → 命中 ✅；`201234` → 命中 ✅；`1234` → 命中 ✅。

若希望进一步降低误报，建议把这条兜底规则改为"仅在正文/主题中含 `验证`/`verify`/`confirm`/`登录` 等词时才启用"，否则干脆移除——前 3 条规则已经覆盖了绝大多数真实验证邮件。

## P2 — 体验、隐私与健壮性

### 2.1 邮件内远程图片自动加载，泄露 IP（与"隐私优先"定位冲突）

**位置**：`MainActivity.kt:1103`（`settings.loadsImagesAutomatically = true`）

`javaScriptEnabled = true` + 自动加载图片，意味着邮件里的追踪像素（1×1 远程图片）会被立即请求，向发件人暴露**用户真实 IP、User-Agent 以及"邮件已被打开"**。README 将"隐私优先"列为设计目标之一，此项与之直接冲突。

**建议**：改为 `loadsImagesAutomatically = false`，并在详情弹窗加一个"显示图片"按钮（用 `evaluateJavascript` 设置 `img.src` 或重新加载）。至少应把 `javaScriptEnabled` 的必要性复核一遍——前 3 条验证码正则 + 链接外跳并不依赖 JS，只有 `mailLinkJs` 注入依赖它。

### 2.2 更新下载流程：无法取消 + 需用户手动重试

**位置**：`MainActivity.kt:863`（`onDismissRequest = {}`）、`:567-575`

- 下载进度对话框的 `onDismissRequest` 是空实现 → 进度卡住或网络极慢时**用户无法取消**，只能杀进程。
- `canRequestPackageInstalls()` 为 false 时跳转"未知来源"设置页后直接 `return`，**下载不会自动开始**；用户授权返回后必须再点一次"在线更新"。

**建议**：对话框允许取消（用一个 `Cancellable` 标志 + 在读取循环里检查，或直接 `call.cancel()`）；授权跳转改用 `rememberLauncherForActivityResult`，返回后自动续跑下载。

### 2.3 `getExternalFilesDir(null)` 的 null 判断在 v1.9 被移除（回归）

**位置**：`MainActivity.kt:580`

```diff
-  val dir = context.getExternalFilesDir(null) ?: return@launch
+  val dir = java.io.File(context.getExternalFilesDir(null), "updates")
+  dir.mkdirs()
```

`getExternalFilesDir()` 在外部存储不可用时会返回 null。旧代码有明确的空判断，新代码去掉了。`File(null, "updates")` 会退化成相对路径 `updates`，在 Android 上通常落到不可写位置 → `mkdirs()` 失败 → 后续写入抛异常 → 被 `catch` 兜住提示"检查更新失败"，不会崩溃，但错误原因会被掩盖。

**建议**：恢复空判断。

```kotlin
val base = context.getExternalFilesDir(null) ?: run {
    withContext(Dispatchers.Main) {
        showDownloadProgress = false
        scope.launch { snackbar.showSnackbar(s.updateFail) }
    }
    return@launch
}
val dir = java.io.File(base, "updates")
```

### 2.4 刷新飞行中修改设置会被旧快照覆盖

**位置**：`MainActivity.kt:1003-1023`（`InboxTab` 的刷新回调）、`:1015`（`onState(state.copy(...))`）

`InboxTab` 收到的 `state` 是**参数快照**（不是活的状态委托）。刷新回调被 `doRefresh` 存下来后由 IO 协程异步调用，此时它闭包里捕获的是**发起刷新那一刻的 state**。因此：

> 点"刷新" → 网络请求在飞行中 → 切到设置页打开深色模式 → 响应到达 → 回调执行 `onState(旧快照.copy(items=...))` → **深色模式被静默回退**。

`MainActivity` 中 `Tab.History` / `Tab.Settings` 的 `onState` 回调读的是活委托 `state`（`:810-834`），所以不受影响；只有 `InboxTab` 这条路径有这个模式问题。

**建议**：把 `onState` 的类型从 `(AppState) -> Unit` 改为 `((AppState) -> AppState) -> Unit`（传 updater 而非快照），或在 `MainActivity` 里提供一个 `update { it.copy(...) }` 帮助函数，让所有写入都基于"写入那一刻"的最新状态。

### 2.5 `rawMessages` / `items` 只增不减，长会话内存单调增长

**位置**：`MainActivity.kt:1013-1014`、`:1746-1760`

每次刷新都把 `receivedata` 原文追加进 `rawMessages`（仅在序列化时截断为 5 条，内存里全留着）；`mergeEmailItems` 按 `from|subject|time` 去重，**只增不减**，无法反映服务端邮件的删除/过期。同时 `count` 取服务端字段、与 `items.size` 不等是常态，用户可能看到"收件数 3"但列表有 10 条。

**建议**：`rawMessages` 在内存里也加 `takeLast(5)`；列表标题改用 `items.size` 或在旁边注明"共 N 封"。

### 2.6 下载完成的 APK 不清理

**位置**：`MainActivity.kt:582`（`app-release.apk` 固定文件名）

安装成功后文件一直留在 `getExternalFilesDir/updates/`，每次更新覆盖同一路径。**建议**在成功拉起安装后删除，或改为按版本号命名 + 定期清理。
